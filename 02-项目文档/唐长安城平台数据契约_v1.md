# 唐长安城知识图谱平台数据契约 v1

版本：`TC-PLATFORM-CONTRACT-1.0`  
对应录入结构：`TC-SCHEMA-1.2`  
日期：2026-08-11

## 1. 用途

本契约规定Excel数据如何转换为现有平台可以导入的四类核心数据：`sources`、`source_chunks`、`entities`、`relations`。它是转换程序、导入校验和平台展示的共同依据。

v1原则：优先复用现有数据库，不新增专用数据库表；唐长安的专业字段暂存入 `properties`，待小样例导入验证后再决定是否拆成独立字段。

## 2. 四类核心数据

### 2.1 sources：来源

来自Excel“来源表”，一条文献、论文、报告或地图对应一条来源。

| 平台字段 | Excel字段 | 规则 |
|---|---|---|
| `id` | 程序生成 | UUID；同一 `source_key` 重复导入时保持稳定 |
| `key` | `source_key` | 保留 `TC-REF-*` 项目编号 |
| `title` | `title` | 必填 |
| `source_type` | `source_type` | 古籍、论文、考古报告、地图等 |
| `payload` | 其余字段 | 作者、版本、出版信息、页码、标识、文件路径、质量等级、备注 |
| `status` | `review_status` | 按第6节映射 |
| `visibility` | 默认值 | 默认 `researcher`；确认版权后可设 `public` |
| `confidence` | 质量等级 | A=0.95，B=0.85，C=0.70，D=0.50；只作来源质量提示 |

### 2.2 source_chunks：来源片段

来自Excel“史料片段”。一行保存一段可独立引用的原文或图面描述。

| 平台字段 | Excel字段 | 规则 |
|---|---|---|
| `id` | 程序生成 | UUID；根据 `chunk_key` 稳定生成 |
| `key` | `chunk_key` | 保留 `TC-CHUNK-*` |
| `source_id` | `source_key` | 转换为来源UUID |
| `original_text` | `content` | 保留审核后的完整片段，不自动缩写 |
| `payload` | 其余字段 | 章节、卷、相关对象、证据类型、备注；页码同时保存原始 `page_label` 与可检索的 `page_start/page_end` |
| `status` | `review_status` | 按第6节映射 |
| `confidence` | `confidence` | 0—1 |

### 2.3 entities：实体

来自各专题表及“研究结论表”“科普内容表”。平台UUID是内部主键，`TC-*`编号必须保存在 `key`。

所有实体统一包含：

```json
{
  "id": "平台UUID",
  "key": "TC-FANG-0001",
  "label": "Fang",
  "name": "兴道坊",
  "aliases": [],
  "properties": {
    "knowledge_layer": "FACT",
    "period_start": "唐",
    "period_end": "唐"
  },
  "source_ids": ["来源片段UUID"],
  "status": "pending_review",
  "visibility": "researcher",
  "confidence": 0.9
}
```

### 2.4 relations：关系

关系只连接两个实体；原文片段不是实体，不作为关系终点，而是写入关系的 `source_ids`。

```json
{
  "id": "平台UUID",
  "key": "TC-REL-0001",
  "source_id": "起点实体UUID",
  "target_id": "终点实体UUID",
  "type": "CONNECTS_TO",
  "label": "连接",
  "properties": {
    "knowledge_layer": "FACT"
  },
  "source_ids": ["来源片段UUID"],
  "status": "pending_review",
  "visibility": "researcher",
  "confidence": 0.9
}
```

## 3. 三层知识标识

所有实体和关系的 `properties.knowledge_layer` 必填：

| 值 | 含义 | 来源 | 默认显示方式 |
|---|---|---|---|
| `FACT` | 基础事实 | 古代文献、考古、测量、可靠复原图 | “基础事实” |
| `INTERPRETATION` | 研究解释 | 现代论文观点或项目组推论 | 显示作者、范围、限制和结论状态 |
| `POPULAR` | 审核科普成品 | 基于前两层加工 | 未审核不得作为正式展项 |

即时AI回答不写入 `entities`。只有经人工选定、需要固定展示或复用的内容，才转换成 `PopularContent` 实体。

## 4. 实体类型映射

| Excel表 | 生成实体类型 | `knowledge_layer` | 主键字段 |
|---|---|---|---|
| 坊功能表 | `Fang` | FACT | `fang_key` |
| 道路分级表 | `Road` | FACT | `road_key` |
| 水渠表 | `Canal` | FACT | `canal_key` |
| 城门表 | `Gate` | FACT | `gate_key` |
| 地形表 | `TerrainFeature` | FACT | `terrain_key` |
| 重要建筑与设施表 | `Building`或`Market` | FACT | `building_key` |
| 坊内平面规则 | `LayoutRule` | FACT或INTERPRETATION，按证据性质判定 | `layout_rule_key` |
| 尺度关系表 | `ScaleComparison` | FACT | `scale_key` |
| 功能分区规则 | `FunctionalZoningRule` | INTERPRETATION | `rule_key` |
| 研究结论表 | `InterpretiveClaim` | INTERPRETATION | `claim_key` |
| 科普内容表 | `PopularContent` | POPULAR | `content_key` |
| 通用实体表 | `Area`、`WaterBody`、`RoadNetwork`等 | FACT | `entity_key` |

辅助对象如 `Area、WaterBody、WaterSource、RoadNetwork、Period、Person、Organization、Document` 可由字段引用触发创建，但必须具有规范编号或进入待补对象清单，禁止生成无编号匿名实体。`RoadNetwork`用于承载针对整体路网的研究解释，不得用某一条具体道路临时代替。

## 5. 关系转换规则

### 5.1 基础空间关系

| 来源表/字段 | 关系类型 | 起点 → 终点 |
|---|---|---|
| 坊功能表 `function_type` | `HAS_FUNCTION` | Fang → Function/Concept |
| 坊功能表 `parent_area_key` | `LOCATED_IN` | Fang → Area |
| 坊间空间关系 | 按表中类型 | Fang → Fang |
| 坊内平面规则 `applies_to_keys` | `APPLIES_TO` | LayoutRule → Fang/Area |
| 道路 `connected_gate_keys` | `CONNECTS_TO` | Road → Gate |
| 道路 `passing_fang_keys` | `PASSES_BY` | Road → Fang |
| 水渠 `water_source_key` | `SOURCED_FROM` | Canal → WaterSource |
| 水渠流经和供水字段 | `FLOWS_THROUGH`、`SUPPLIES` | Canal → Area/Fang/Building |
| 城门 `connected_road_keys` | `CONNECTS_TO` | Gate → Road；与道路侧重复时合并 |
| 地形 `covered_area_keys` | `COVERS` | TerrainFeature → Area/Fang |
| 建筑所在区域 | `LOCATED_IN` | Building/Market → Area/Fang |
| 建筑连接道路 | `CONNECTS_TO` | Building/Market → Road |
| 建筑邻近水渠 | `NEAR` | Building/Market → Canal；不得推导为供水 |

### 5.2 研究解释关系

研究结论必须生成 `InterpretiveClaim` 实体，再通过 `subject_relation_type` 连接解释对象：

- `INTERPRETS`：对对象作总体解释；
- `EXPLAINS`：解释机制或原因；
- `REFINES`：修正或限制既有模型；
- `SUPPORTS`：为另一结论提供支持；
- `CONTRADICTS`：与另一结论冲突。

研究结论实体的 `properties` 至少保存：`claim_text、claim_type、proposed_by、basis_text、reasoning_chain、scope、limitations、claim_status`。

### 5.3 科普成品关系

`PopularContent` 可通过 `SUPPORTED_BY` 指向：

1. `InterpretiveClaim`实体；
2. 基础事实实体，如Road、Fang、Gate；
3. 规则实体，如LayoutRule。

直接原文片段写入 `PopularContent.source_ids`，不生成“科普内容→片段”图谱边；同时在 `properties.direct_evidence_links` 保存原表中的 `support_role、display_order、public_explanation、is_visible、review_status`，以便平台正确控制显示顺序和公开范围。若需要引用某一条事实关系，则把该关系编号写入 `properties.supported_relation_keys`；v1不把关系再实体化。

## 6. 审核状态映射

| Excel状态 | 平台状态 | 是否公开 |
|---|---|---|
| 空白、未开始 | `draft` | 否 |
| 待审核、等待确认 | `pending_review` | 否 |
| 审核通过 | `approved` | 否，需创建发布版本 |
| 审核未通过、退回修改 | `rejected` | 否 |
| 存在争议 | `disputed` | 只在研究授权范围显示 |
| 已发布 | `published` | 按visibility决定 |

转换程序不得把“审核通过”直接改成“published”。发布必须经过平台的版本发布操作。

## 7. 证据规则

1. FACT实体和关系至少绑定一条 `source_chunk`，否则只能保持 `draft`。
2. INTERPRETATION至少绑定论文片段，并填写作者、适用范围和限制。
3. POPULAR正式发布前必须至少连接一条研究结论或事实实体，并具有直接片段证据或可沿关联追溯到片段。
4. 地图判读、古籍直述、现代研究和项目推论必须保留不同 `evidence_type`。
5. 多个 `chunk_key` 用分隔符填写时，转换程序拆成UUID数组，不把整串当成一个编号。
6. 引用编号不存在时整条记录进入错误报告，不导入数据库。

## 8. 编号与UUID

- Excel中的 `TC-*` 是业务编号，长期稳定、人工可读；
- 平台 `id` 使用UUID；
- UUID按“数据集命名空间＋业务编号”稳定生成，保证重复导入得到同一UUID；
- 更新相同 `TC-*` 记录时创建平台版本，不生成重复实体；
- 不允许用名称作为唯一键。

## 9. 导入顺序

1. 校验工作簿版本和必填字段；
2. 导入 `sources`；
3. 导入 `source_chunks`；
4. 生成并导入基础实体；
5. 生成并导入基础关系；
6. 导入 `InterpretiveClaim`及其关系；
7. 导入审核科普成品及 `SUPPORTED_BY`；
8. 扫描重复编号、悬空关系、缺失证据和状态错误；
9. 在平台中提交审核；
10. 人工验收后创建发布版本。

## 10. 首批导入包范围

首个导入包只使用“小型样例”中已有数据，不导入空白占位行。科普样例 `TC-POPULAR-0001` 保持 `pending_review`，不得发布。

通过标准：来源和片段可查看；实体关系可检索；点击实体可回溯原文；研究解释有明显标识；科普回答能显示依据；重复导入不会产生重复数据。

## 11. v1暂不处理

- 不直接导入完整108坊和全量道路；
- 不删除青瓷演示数据；
- 不建立专门的科普内容数据库表；
- 不把每条关系实体化；
- 不在本阶段实现地图界面；
- 不自动发布任何导入记录。
