## 一、工作总览

### 目标

通过逐份资料的全文逐段通读，尽可能全面、详细地从可靠史料中提取唐长安城的实体、关系和史料摘录，形成可演示、可搜索、可供 AI 问答的知识图谱数据库。

### 核心原则

- **逐段通读，不跳段**：在确定的范围内，每一段都完整阅读。
- **全量登记，不遗漏**：不仅提取预设的核心条目，还提取文中出现的所有可录入对象。
- **来源先行**：每一条实体和关系都必须有可追溯的来源。
- **分批审核，不跳步**：每完成一批即交付审核，确认后追加到 Excel。

### 提取方法

采用 **AI 直接读原文 + 逐条手写** 的方式：AI 阅读史料原文（epub 文字版），逐段理解文意后手动提取实体和关系，不依赖正则表达式或 LLM API 调用。此方法在宫城摘录中验证有效，能确保提取质量。

### 数据流

```
用户提供 epub/PDF
       ↓
AI 逐段通读原文，全量提取（AI 直接读原文 + 逐条手写）
       ↓
AI 生成本批"审核表"（来源 + 实体 + 关系 + 史料片段）
       ↓
用户逐条审核：✓ 通过 / ✗ 修改 / – 删除
       ↓
AI 写入 Excel 模板对应工作表（来源表 → 实体表 → 关系表 → 史料片段）
       ↓
用户运行"一键导入长安城数据.bat"
       ↓
脚本校验 → 生成 all_in_one.json → 后端读取 → 网页/图谱/AI 显示
```

## 三、每份资料的处理流程

每份资料的具体分批计划和检索细节，详见该资料的**文献检索清单**（存放于 `01-指导文档\文献检索清单\`）。通用流程如下：

1. **结构探查**：确定全书分卷结构、扫描边界（从哪读到哪）、哪些部分与项目相关。
2. **逐段通读**：在确定的范围内逐段阅读，每段执行完整提取格式。
3. **全量登记**：所有发现的实体和关系记入全量登记表。
4. **分批交付**：按文献检索清单中规划的批次，每完成一批即生成审核表交付用户。
5. **审核确认**：用户逐条确认后，AI 将数据写入 Excel。
6. **导入系统**：用户运行一键导入脚本。

## 六、实体类型与关系类型

### 实体类型（8 类）

| 代码 | 中文 | 示例 |
|------|------|------|
| Fang | 坊 | 平康坊、崇仁坊 |
| Market | 市 | 东市、西市 |
| Street | 街道 | 朱雀大街 |
| Gate | 城门 | 明德门、朱雀门 |
| Building | 建筑 | 大明宫、大雁塔 |
| Person | 人物 | 宇文恺、玄奘 |
| Event | 事件 | 大兴城始建 |
| Reference | 史料 | 《长安志》（可选） |

> 全量扫描中超出以上类型的对象，优先映射到最接近的现有类型，notes 中标明原始含义。大量出现时与用户讨论是否新增。

### 关系类型（13 类）

| 代码 | 中文 | 适用情况 |
|------|------|----------|
| LOCATED_IN | 位于…内 | 建筑位于坊、区域内 |
| LOCATED_ALONG | 位于…沿线 | 坊、市位于街道沿线或一侧 |
| EAST_OF | 位于…东侧 | 明确方位关系（"X東為Y"、"X門東Y門"、"次東Y"） |
| WEST_OF | 位于…西侧 | 明确方位关系 |
| SOUTH_OF | 位于…南侧 | 明确方位关系 |
| NORTH_OF | 位于…北侧 | 明确方位关系 |
| NORTHEAST_OF | 位于…东北侧 | 复合方位关系 |
| ADJACENT_TO | 相邻 | 两个坊、市或区域相邻 |
| NEAR | 靠近 | 空间接近但非直接相邻 |
| FACING | 相对/正对 | 两建筑/城门南北或东西正对（如"南直承天門"） |
| CONNECTS_TO | 连接 | 街道与城门、区域的连接 |
| ASSOCIATED_WITH | 相关 | 人物与地点、建筑的关联 |
| INVOLVED | 涉及 | 事件涉及建筑、地点或人物 |

> **v5 变更说明**：
> - 新增 5 类：EAST_OF、WEST_OF、SOUTH_OF、NORTHEAST_OF、FACING（基于宫城摘录审核经验补充）
> - 移除 3 类：PLANNED（合并入 ASSOCIATED_WITH）、INITIATED（合并入 ASSOCIATED_WITH）、CENTER（合并入 LOCATED_IN）
> - 从 v4 的 10 类调整为 13 类

## 七、字体与字形规则

> v5 新增。基于宫城摘录审核过程中确立的字体标准。

### 简体字段（使用简体字录入）

以下字段使用简体中文书写：

- **name**：实体名称（如"承天门"而非"承天門"）
- **aliases**：别名（如"广阳门,昭阳门,顺天门"而非"廣陽門,昭陽門,順天門"）
- **description**：现代中文描述
- **relation_label**：关系描述性短语
- **note**（关系表、史料片段表）：备注说明

### 繁体字段（保留原文繁体）

以下字段保持史料原文的繁体中文原貌：

- **description_quote**：实体描述的原文引用
- **evidence_quote**：关系证据的原文引用
- **content**（史料片段表）：原文内容
- **name_traditional**：繁体名称（如有需要）

### 转换工具

使用 OpenCC（opencc-python-reimplemented）的 `t2s`（繁体→简体）转换器进行批量转换。转换时须严格区分"应转简体"和"保留繁体"的字段。

## 八、质量规则

1. **编号唯一**：同一编号不能重复，只能使用英文、数字、短横线和下划线。
2. **来源先行**：source_key / evidence_source_key 必须指向已存在的来源。
3. **关系两端存在**：关系表的 source_key 和 target_key 必须指向实体表中已有的实体。
4. **置信度**：原文直述 ≥ 0.90，推理 0.75–0.85，存疑 ≤ 0.70。
5. **争议保留**：不同资料说法矛盾时保留不同来源，notes 中说明，不擅自选择。
6. **不改代码**：所有修改只通过 Excel 模板进行。
7. **字体规则**：简体字段用简体字，繁体字段保留原文繁体（详见第七节）。
8. **原文摘录保持原貌**：content、description_quote、evidence_quote 字段直接写原文，不加书名前缀，不做改写，不截断。
9. **关系标签描述性**：relation_label 和 note 使用描述性文字，不使用通用标签或直接粘贴原文。

## 附录 A：已确立的工作原则

以下原则在第 0 批审查和宫城摘录审核过程中逐步确立，后续批次应持续遵循：

1. **description 用现代中文**：简洁可读，保留关键信息
2. **description_quote 保留原文**：繁体中文逐句照录，用于溯源
3. **全量提取**：凡文献中出现的命名实体全部录入，不做取舍
4. **分类必须准确**：城门/Gate 与内门/Building 严格区分；宫殿区（大型建筑群）与殿宇（单体宫名建筑）严格区分
5. **每步修改必须经用户确认**：先报告问题和方案，用户确认后再执行
6. **relation_label 和 note 用描述性文字**：不使用通用标签或直接贴原文
7. **方位关系需覆盖古文模式**：X之東/西/南/北、東為X、X門東Y門、次東Y、南直X 等
8. **仅改类别不删条目**：除非明确为非唐代实体（如汉代旧宫），否则不删除
9. **不好归类的放其他**：宁可保守分类，不强行归入不合适的类别
10. **字体严格区分**：简体字段用简体，繁体字段保留原文（详见第七节）
11. **evidence_quote 独立字段**：关系的原文证据作为独立列记录，不与 note 混用

## 附录 C：风险提示

- **扫描版 PDF 阅读速度慢**：每页需导出图片后视觉识别。建议优先使用 epub 文字版。
- **古籍竖排繁体识别可能有误**：尤其是夹注小字和生僻字，提取时标注可疑之处供用户确认。
- **实体类型映射**：全量扫描会发现超出预设 8 类的对象，需要灵活映射并与用户确认。
- **编号冲突**：如果团队其他成员同时在录入 Excel，需要统一编号分配。
- **跨资料一致性**：同一实体在不同资料中可能有不同说法（方位、年代、别名），按争议处理规则保留而非强行统一。
